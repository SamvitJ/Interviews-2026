## What to work on

**Mechanism lags the fix.** This is the dominant theme. On m3 the right change
("normalize before the `seen` check") came out within a couple of minutes, but
the *why* took four rounds of pushing and still needed the key fact supplied:
a set files an object under the hash it had at insertion time and never re-files
it. Answering "the seen logic is broken" when asked to explain why the seen
logic is broken is restating the symptom. In a real round this reads as
pattern-matching rather than understanding, and it's the difference between a
hire and a strong hire.

Drill: after every fix, say the causal chain out loud in one sentence with no
reference to the test output. "X is stored under hash H1; mutation changes it to
H2; lookup at H2 misses the bucket at H1." If that sentence doesn't come out
clean, the mechanism isn't owned yet.

**Axis 2 dropped as difficulty rose** (3 → 2 → 1 → 2), which is the predicted
reversion and worth knowing about yourself.

**One evidence miss on m2.** Initial read was "a secondary lexicographic sort
isn't being applied" — but the output was `['zebra', 'mango', 'apple']`, exact
reverse alphabetical. The evidence said "applied and reversed," not "absent."
Updated cleanly when pushed, but the first pass looked at the output and didn't
actually read it.

## Facts that were missing

All three are read-once-own-forever:

- **Python's sort is stable.** Equal keys keep input order. This is the whole
  reason `sorted(sorted(x, key=secondary), key=primary, reverse=True)` works.
- **Sets hash at insertion.** Mutating a stored object's hash-relevant state
  makes it permanently unreachable. Corollary: don't put mutable objects in sets.
- **`return` inside `finally` discards a propagating exception.** Same for
  `break` and `continue`.

Also worth keeping: `math.floor(a / b)` does float division first and loses
precision on large ints; `a // b` stays exact.
