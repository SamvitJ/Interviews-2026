## To fix, in priority order

**1. Theorizing where interrogation is cheaper.** On m2, several minutes went
into reasoning about regex behavior, landing on "it makes two matches." One
`re.findall` call settled it instantly and showed it was one. The interpreter
was available the whole time.

Contrast m4, done right: hypothesis stated, two-line experiment written, *and
the order flipped as a control*. The only 3 on that axis. The difference wasn't
difficulty — m4 is harder. It was reaching for the interpreter instead of the
head.

**2. Adding machinery before establishing need.** m2 acquired a `while` loop
and a recursive call; both came out under questioning and neither was ever
needed. m3's retry had a counter and a loop bound doing overlapping jobs — and
the off-by-one lived precisely in that overlap. Default to the smallest edit
that could work, then justify anything beyond it.

**3. Pacing.** Time is not going to localization, which is consistently fast.
It goes to the stretch between "I know where it is" and "I've confirmed what
it is." In a real 45-minute round, two bugs would have been finished.

**4. Reading failure output more slowly.** On m4 the first read was that the
count was wrong. It was right in all three cases — *"one number correct, the
other always exactly zero"* is the entire fingerprint. Recovery was fast, but a
careful first read skips a step.

## Bug-by-bug

### m1 — `strip_extension` (easy, 4m target, ~11m)

`str.strip(".txt")` treats its argument as a set of characters stripped from
both ends, not a suffix. `"report.txt"` → `"repor"`.

Ran first and used the output to narrow. Correctly identified that `notes.txt`
passes by luck (`s` isn't in the strip set). First fix attempt was
`.replace(".txt", "")`, self-flagged as imperfect, and the counterexample
(`"hello.txt.txt"`) was produced on request. Settled on `removesuffix(".txt")`.

Docked on fix quality: reported the fix as saved when the file still held the
previous version, and did not add a regression test for the counterexample
already identified. The suite went green against the version known to be wrong.

### m2 — `strip_tags` (medium, 6m target, ~20m)

`<.*>` is greedy, so one match spans the first `<` to the last `>`, swallowing
the text between tags. Fix: `<[^>]*>`.

Fastest localization of the set — pointed at the regex immediately. But the
mechanism was reasoned about rather than tested, producing a wrong model ("two
matches") that `re.findall` corrected instantly. Detoured through `<.>` and
`</.>`, which special-cases single-character tags and breaks on `<div>`.

Fix quality 1: the correct pattern arrived wrapped in a `while` loop *and* a
recursive `strip_tags` call. Both were removed only under questioning. The
original was a single `return re.sub(...)`; the whole bug was one character
class.

### m3 — `process_batch` (hard, 10m target, ~19m)

The retry re-sends the whole batch, so records that already landed get sent
twice: `['a','b','a','b','c','d']`. Fix is retry at record granularity.

Diagnosed immediately and correctly from the `got` list, and spotted that the
third test passes only because the failure is on the first record. The first
retry loop had two inverse defects — it sent `retries + 2` times without
raising, and raised on a record that succeeded on the final allowed attempt.
Hand-tracing missed the off-by-one because the `while` test precedes the
increment; an empirical run found it. Second version was correct.

Tighter form, discussed after:

```python
for record in records:
    for attempt in range(retries + 1):
        try:
            sink.send(record)
            break
        except TransientError:
            if attempt == retries:
                raise
```

`range(retries + 1)` makes the attempt count and the loop bound the same
expression, so the off-by-one is unrepresentable. Bare `raise` preserves the
sink's original exception and traceback. It is also the smaller diff against
the original, whose only mistake was nesting the `for record` loop inside the
retry loop.

### m4 — `summarize` (hardest, 10m target, ~17m)

`big` is a generator expression. `sum(1 for _ in big)` exhausts it, so the
second `sum` sees nothing and returns 0. Fix: `[` instead of `(`.

Best hypothesis work of the set. Misread the output initially as a wrong count,
then recovered and pinned exhaustion with a clean experiment, including flipping
the print order as a control. First proposed fix (single pass accumulating both
values) was correct but larger than necessary; the one-character fix came on
request. Single-pass remains the right call when the data is too large to
materialize.
